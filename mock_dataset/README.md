# Amazon chatBI 模拟数据集

用于在真实数仓表结构确认前,先跑通 NL2SQL、指标 RAG 和评估流程。**全部数据为随机生成,不代表任何真实业务。**

## 数据概况

- 时间范围:2026-04-21 至 2026-10-17(共 180 天;汇率表到 2026-10-18)
- 4 个店铺站点:US / CA / UK / DE,金额均为站点原币,折算人民币需通过 `exchange_rates`
- 13 个 SKU,按站点展开为 50 个 (店铺, MSKU)
- 库存快照只有最近 90 天(2026-07-20 起)

| 表名 | 说明 | 行数 |
| --- | --- | --- |
| dim_stores | 店铺站点维表 | 4 |
| dim_products | 商品维表 | 50 |
| exchange_rates | 汇率表 | 804 |
| amz_order_items | 订单明细表 | 11,318 |
| amz_ads_daily | 广告日报表 | 8,912 |
| amz_traffic_daily | 流量日报表 | 7,986 |
| amz_fba_inventory | FBA库存快照表 | 4,400 |
| amz_settlement | 结算明细表 | 33,780 |
| amz_returns | 退货明细表 | 463 |

表结构与 `amazon_tables.json` 一致。`amz_settlement` 和 `amz_returns` 额外多一个自增主键 `id`,仅模拟库使用。

## 导入 MySQL

```bash
# 1. 建库建表
mysql -u <用户> -p < schema.sql
# 2. 导入数据(在本目录执行,需要开启 local_infile)
mysql --local-infile=1 -u <用户> -p chatbi_demo < load_data.sql
```

如果提示 local_infile 被禁用,先执行 `SET GLOBAL local_infile = 1;`。

## 内置的测试场景

数据里刻意埋了一些业务现象,方便检验分析类问题(例如"为什么销售额下降"):

| 场景 | 位置 | 现象 |
| --- | --- | --- |
| 断货 | 宠物自动喂食器 PT-001,US 站,2026-08-10 至 08-24 | 销量为 0,库存为 0,Buy Box 为 0 |
| 广告浪费 | 电动打蛋器 KT-003,UK 站,2026-09-20 至 09-26 | 广告点击约放大 3 倍,订单没有增加,ACOS 飙升 |
| 销量下滑 | 运动水壶 OD-003,US 和 UK 站,2026-10-05 起 | 10-05 至 10-11 约降一半,之后约降 30% |
| Buy Box 偏低 | 折叠露营椅 OD-002,DE 站 | Buy Box 占比约 55%~72% |

## 数据中的口径陷阱

- 订单状态包含 Shipped / Unshipped / PartiallyShipped / Pending / Canceled,最近 3 天的订单大部分还没发货
- 一个订单可含多个商品行(同一个 `order_id` 多行),统计订单数必须 `COUNT(DISTINCT order_id)`
- 结算入账比下单晚 3 到 8 天;退货比下单晚 5 到 30 天,所以近期退货率偏低
- 库存年龄分档之和等于可售库存加预留库存
- 广告日报里有只有点击、没有订单的行

## 验证说明

28 个指标的 SQL 已经用这份数据运行,并与独立的 pandas 计算逐项对账,结果一致。沙箱里没有 MySQL,验证是通过把 SQL 转译到 SQLite 完成的,因此**还没有在真实 MySQL 上执行过**。导入后建议把指标字典里的 SQL 在 MySQL 里再跑一遍。
